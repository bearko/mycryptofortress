## 方針

- **縦切り優先**: まず「1 レベル・弓ロールのヒーローのみ」で**ラン → トークン → ツリー → 再挑戦**のループを最短で成立させ、面白さを早期に検証する。以降はタワー・状態異常・レベルを横に広げる。
- **1 SPEC = 1 PR 前後**: 各フェーズの項目は SPEC-101 以降として起票し、仕様駆動フロー（[AGENTS.md](../AGENTS.md)）に従う。
- **データ駆動**: バランス値は JSON に置き、調整はデータ PR で行う。
- 規模感: S = 1 PR / 半日〜1 日、M = 1〜3 PR、L = 3 PR 以上。

## 全体像

```
Phase 0  撤去と基盤          ──▶ 空のv2が起動・アセット取込・CI
Phase 1  縦切りプロトタイプ   ──▶ Lv1 を弓ヒーローだけで遊べる  ★初プレイアブル
Phase 2  メタ進行 MVP        ──▶ 負けても進むループが回る      ★コアループ検証
Phase 3  ヒーローと状態異常   ──▶ 5 ロールのヒーロー + 幻獣砲 + Lv1〜6
Phase 4  宝珠とマイルストーン ──▶ 元素エンチャント + 自動化 + Lv7〜9
Phase 5  本編完成            ──▶ Lv10 + 50 チャレンジ + 実績   ★v1.0（本編）
Phase 6  エンドゲーム        ──▶ プレステージ / 宝珠レベル / エンドレス
Phase 7  仕上げ              ──▶ モバイル最適化・性能・英語化
```

## リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| Outhold 詳細数値が非公開 | バランス設計の手戻り | 数値は独自設計前提。Phase 2 のプレイテストで曲線を早期確定 |
| ツリーが肥大化して管理困難 | 整合性崩れ | JSON スキーマ + データテスト + ツリー可視化ツール |
| スマホでの性能 | 敵・弾・状態異常の多さ | プール化・tick 集約・描画の間引き |
| 序盤グラインドの冗長さ（Outhold への批判点） | 離脱 | 序盤トークン曲線を緩め、1 時間以内に 3 系統を触れる設計 |
| アセットの利用条件 | 公開停止リスク | MCH 公式ガイドライン確認を HITL に含める |
